# 仓库治理与资产隔离设计

**状态：** 已评审，待执行

**日期：** 2026-10-19
**范围：** 仅定义目录结构、Git 边界与忽略规则；不在本设计阶段移动、删除、覆盖或重建任何现有文件。

## 1. 背景与目标

`D:\cqt_platform` 当前同时承载 Qt 桌面应用、旧版 Python 原型、训练后端、数据集、模型、频谱图、交付包、构建目录、日志与本地环境。根目录的 Git 仓库尚无首提交；`aircraft_project` 与 `aircraft_project/cpp_app` 还存在嵌套 Git 边界。历史副本与运行产物混在源码附近，使版本控制、检索、构建复现和误提交风险都不可控。

本设计建立一个单主仓库模型：`D:\cqt_platform\aircraft_project\cpp_app` 是唯一正式开发仓库。所有可审查、可重建的产品源码进入该仓库；体积大、运行时生成或历史性的资产与其物理隔离，并且不进入 Git。

## 2. 目标边界

### 2.1 正式主仓库

`D:\cqt_platform\aircraft_project\cpp_app` 是唯一允许日常提交、分支开发、构建和自动化测试的仓库。其应追踪：

- `src/`：Qt/C++ 产品代码。
- `tests/`：自动化测试及小型、脱敏、可审查的测试夹具。
- `docs/`：当前产品、架构、运维与治理文档。
- `scripts/` 与 `tools/`：可复现的构建、打包、诊断工具源码。
- CMake/Qt 配置、依赖清单、启动脚本、示例配置。
- `dji_training_backend_v5/` 中被桌面应用调用的训练后端源码、测试和固定配置。

### 2.2 工作区与资产

`D:\cqt_platform` 是工作区，而不是正式 Git 仓库。未来资产应归拢到以下不受 Git 管理的目录；创建与实际迁移须作为后续单独任务执行：

```text
D:\cqt_platform\
├── aircraft_project\
│   └── cpp_app\                 # 唯一正式 Git 主仓库
├── _assets\                     # 本机资产，始终不进 Git
│   ├── captures\
│   ├── datasets\
│   ├── models\
│   ├── spectrograms\
│   ├── runs\
│   ├── releases\
│   ├── backups\
│   ├── archives\
│   ├── envs\
│   ├── logs\
│   └── manuals\
└── _workspace\                  # 编辑器、代理与临时状态，不进 Git
```

真实采集物、数据集、模型权重、训练输出、频谱图、发布包、备份、日志、PDF 手册和 Python 环境均属于 `_assets`。主仓库的 `data/` 仅保留运行时路径约定，不保存真实采集数据。

### 2.3 历史与实验资产

旧 Python 原型、`cpp_app_demo_sweep`、AutoDL 镜像、历史交接包与压缩文件不再作为开发入口。它们应被记录为历史或实验资产，包含用途、来源、最后维护时间和主仓库替代入口。此设计不删除、压缩、重命名或移动这些内容。

根目录未初始化完成的 Git 与 `aircraft_project` 的旧 Python Git 均不用于后续开发；它们的退役或归档必须在资产副本验证完成后，经独立确认后再实施。

## 3. Git 规则

### 3.1 追踪准则

仅追踪重建产品所必需且能被代码评审的内容。发布物必须从干净的主仓库提交通过脚本生成，输出到被忽略的 `dist/` 或工作区 `_assets/releases/`。

不使用 Git LFS 保存模型、数据或发行包。每个外置资产应在文档或资产清单中记录来源、获取方式与校验值。

### 3.2 忽略规则

保留已有的 CMake、Python 缓存、硬件采集和运行状态忽略规则，并补充下列主仓库根级规则：

```gitignore
# Local build, package, backup, and replay outputs
/dist/
/backups/
/fullflow-*/
/$out

# Local executable state and generated data
/data/
/captures/
/state/
*.cap
*.iqraw
*.npy
*.pth
*.pt
```

最终落地时应根据现有 `data/` 的真实用途审查上述规则，确保只保留目录约定或显式追踪的小型测试夹具。不要用全局 `*.zip`、`*.dll` 等宽泛规则；应按已知产物目录或明确文件名忽略，避免误隐藏将来需要评审的依赖。

新增 `.gitattributes`，统一文本文件换行策略，并将已知二进制类型标注为非文本差异比较对象。

### 3.3 提交纪律

1. 禁止以 `git add -A` 建立基线。先生成并审查“源码、文档、脚本、资产”分类清单。
2. 既有未提交变更按照产品源码、训练后端、测试、文档/脚本分组审查并独立提交。
3. 每组提交必须至少完成对应构建或测试；硬件接入功能使用离线、仿真或 dry-run 验证，除非另获明确授权。
4. 新功能分支使用 `codex/<主题>` 命名。
5. 本机 VISA/UHD 路径、设备连接参数及密钥只保留已忽略的本地配置；仓库只保存安全的示例模板。

## 4. 分阶段执行方案

### 阶段 A：只读基线

导出三个现有 Git 目录的状态、未跟踪文件分类和重要资产的文件数、大小与哈希。不得初始化根 Git、删除旧 `.git`、移动数据或修改设备配置。

### 阶段 B：主仓库规则

在 `cpp_app` 中新增治理文档、精确 `.gitignore`、`.gitattributes` 和本地配置模板。使用 `git check-ignore` 验证每一类产物均被隔离，同时验证源码、测试、文档与脚本没有被误忽略。

### 阶段 C：提交边界整理

将现有 `cpp_app` 改动按产品源码、训练后端、测试、文档/脚本分组。每组单独审查、测试和提交；任何用途不明的文件均不纳入提交。

### 阶段 D：资产迁移（独立批准后）

先将资产复制到 `_assets`，逐项比对文件数、大小和哈希。再将应用配置切换到新路径，并进行一次完整构建与运行验证。原文件保留；是否归档旧副本必须另行确认，不能自动进行。

### 阶段 E：遗留树退役

为旧 Python 原型、演示副本和 AutoDL 镜像增加维护状态说明，使其不能再被误认为主开发入口。其物理归档、迁出或删除均不属于本设计的自动执行范围。

## 5. 验收、回滚与风险控制

验收条件：

- 在干净克隆的 `cpp_app` 中，使用公开的依赖说明可完成离线构建和自动化测试。
- `git status` 只显示有意的源码、测试、文档或脚本修改。
- 生成数据、模型、打包物和本机状态不会再进入待提交列表。
- 新成员可通过主入口文档识别主仓库、资产位置和遗留资料状态。

规则、文档和构建脚本的修改均可通过 Git 提交回退。资产迁移始终采用“复制、校验、切换、验证”的流程，原文件全程保留；路径切换失败时只需恢复本地配置，不恢复或重写数据。任何涉及旧 Git 目录、真实数据、模型、交付包或设备配置的删除、覆盖、重建、重置和迁移，均需要额外的明确确认。
